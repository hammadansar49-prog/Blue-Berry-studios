# Release audit: startup, persistence and local server

## Fixed and verified

- Desktop now uses `http://localhost:17843` on every launch. Previous random ports created a different localStorage/Firebase origin each launch.
- A second instance focuses the first. A port conflict shows an actionable error and quits; it never changes the storage origin or silently falls back to `file://`.
- Local HTTP responses are restricted to shipped public web files and assets. Electron source, repository metadata, package manifests and arbitrary files are rejected. Unexpected Host headers are rejected.
- Main-window navigation is restricted to its app origin. External HTTP(S) links open in the system browser; other protocols are denied for new windows.
- Browser-based Google sign-in callbacks require a cryptographically random, expiring, single-use state generated by the desktop app. Sign-in IPC validates its sender. Failed callbacks no longer display a success message in the helper page.
- Firebase 10.12.2 and XLSX 0.18.5 are bundled with licenses; app and Google-helper scripts load locally. Firestore IndexedDB persistence is enabled before reads through fbPersistenceReady. New cloud authentication still requires connectivity. Missing/corrupt SDK handling remains defensive.
- `node --test tests/startup.test.js`: six regression tests cover stable origin, private file/host rejection, unsolicited/replayed Google callbacks, missing Firebase SDK startup, local script availability and a real spreadsheet export/import round trip.

## Existing-installation data

Old random-port browser storage is not deleted or automatically merged into the new fixed origin. Before upgrading an installation with real records, export its backup while the old session is open and confirm its cloud sync if used. Restore the verified backup after upgrading if needed. Blindly choosing an old origin could restore another user's or an obsolete store's records.

## Cloud authorization changes and deployment requirement

Repository Firestore rules now restrict store reads to authenticated owners and explicit member UIDs. Store writes remain owner-only because data is one complete JSON document: allowing staff to replace it would also let staff change roles and other protected data. Mapping ownership is immutable, deletes check existing ownership, and branch lookup is restricted to already-authorized accounts. Public collection listing is denied for branch code registries.

Branch codes are identifiers, not authentication credentials. Branch login now explicitly requires signing in with an owner or linked staff account first; unauthenticated code-only access is unsupported. Existing staff account creation adds the Firebase UID to the owner's membership list. Existing code-only branch IDs do not become authenticated Firebase users by appearing in that list.

**Release limitation:** staff/branch cloud writes need a scoped server-side mutation API or separate protected documents. They cannot be safely enabled by granting whole-store write access. Owner cloud workflows remain supported. Rules edits are local only until deployed to the Firebase project; current deployed rules were not inspected or changed. A Firebase Rules emulator/account integration test is still needed before certifying cloud privacy and permissions. Existing cloud documents containing plaintext staff credentials should be sanitized by the owner after securing deployed rules.

## Hardware/platform limits

Electron 22 is a legacy runtime chosen for Windows 7/8 support. This audit does not constitute testing on those systems. Physical printer output, drivers, USB/network status reporting, cutters and cash drawers require checks on client hardware. Cloud authentication and browser callback behavior need a real account integration test.
